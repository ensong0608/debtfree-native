# T-271 emulator lag — blocked, partial evidence (2026-11-14)

The emulator itself is a confirmed part of the problem: SurfaceFlinger reports Google SwiftShader software OpenGL, despite WHPX being usable. During the investigation Android displayed “System UI isn't responding” while the Expo development launcher was showing, before the financial screens loaded. This establishes system-level unresponsiveness, not that software rendering alone caused all lag. Host samples before restart were 84.7%, 80.2%, 81.2% total CPU, with approximately 4,090 MB available RAM out of 16,516,804 KiB physical. Emulator process working set was about 3,009 MB; host process CPU totals were lifetime counters, not interval rates. Hardware: i7-10750H, 12 logical processors, Intel UHD and NVIDIA GTX 1650 Ti. Guest config: 2 cores, 2 GB, 1080x2400, 60 Hz. Guest cpuinfo over an earlier 30-second window showed dev-client process 75%, SurfaceFlinger 31%, graphics composer 23% (percent of one core, not isolated workloads); dev-client PSS was 122,622 KiB. After cold restart an unrelated 5-second window showed launcher 32%, system_server 23%, composer 17%, System UI 9.7%, SurfaceFlinger 9.7%. These samples are not matched benchmarks.

The installed app is an Expo development client. It displayed “Failed to connect to localhost/127.0.0.1:8081”; initially no host listener existed. Started Metro temporarily; it listened on 127.0.0.1:8081, but the application did not reach its screens and the System UI ANR prevented verification. Metro was stopped afterwards. Debug execution and bundling can add cost and the missing server clearly prevents the dev client loading; neither quantifies normal app interaction overhead.

Reversible graphics experiment: backed up the AVD config to `config.before.ini`, shut down using the bound device command, changed GPU enabled to yes, mode host and forced cold boot. The supported device launcher started with `-no-window -gpu auto`, and SurfaceFlinger still reported SwiftShader. Thus no graphics improvement was verified; restored the original config byte-for-byte. After restart host CPU samples were 35.8%, 35.4%, 31.1%, available memory 5,221–5,104 MB, but boot phase and workloads differed. No speedup can be attributed to the change. The emulator remains running; the task's bound session was closed successfully. No AVD or app data wiped, no live financial writes, app code changes or builds.

Current source inspection: `src/FiveTabShell.tsx:75` invokes only the selected tab builder. Home memoizes payoff and schedule work, Transactions memoizes maps and schedules and has module-level date formatters. This does not mean all formatters are cached: `src/finance/calendar.ts:48` constructs one per householdDate call and several screen formatters are constructed inline. No profiling ties these paths to the observed ANR. No comparable old benchmark or installed-build provenance exists, so recent development as a cause remains unknown. Previous accumulated gfxinfo (662 frames, 163 janky, 26 ms median) had unknown workload and is not a controlled baseline.

The first relaunch command failed: “Android app com.debtfree.nativetest remained foreground after close”; the instructed debug retry succeeded. The subsequent System UI ANR and failure to load the app blocked controlled navigation, app-versus-system comparison and before/after repair verification. Next investigation needs a supported launcher configuration that allows hardware GPU selection, plus a stable dev-client connection and matched system/app workload; do not assume host graphics works or that an app regression occurred.
