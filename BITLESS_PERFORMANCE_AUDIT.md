# BitLess performance audit and scalability assessment

Audit date November 20, 2026. Checkout `feature/signed-in-recovery-android-delivery` at `d92ab74`, including existing working-tree edits to Transactions and tab context. Source, isolated PostgreSQL 17.11 and synthetic Windows Node 24.20.0 measurements are identified below.

## A. Executive summary

**The strongest measured bottlenecks are the transaction cache on Save and full-history retrieval on synchronization.** The code also performs avoidable work on tab changes and while typing. Its contribution to the owner's observed lag still needs a native trace.

1. **One transaction rewrites the entire local transaction cache twice.** The cache portion alone reached **101 ms p95 at 1,000 prior transactions** and **629 ms at 5,000** in a synthetic JavaScript benchmark using an in-memory storage adapter. Actual native SecureStore latency is unmeasured. The RPC runs between these two cache stages.
2. **Synchronization repeatedly authorizes and sorts the same history rows.** The current 5,000-row read took **2.11 s** for 11 SQL queries and returned **4,997 unique IDs**. Unstable ordering lost three distinct rows in that run. A scratch household/date/ID index and keyset query took **0.32 s** and returned **all 5,000 unique IDs** with the existing policy.
3. **Visited tabs remain mounted and share context updates.** History recreates filter dependency arrays and repeats filtering and sorting on unrelated renders. Budget, Progress and Home have recurring derivation work. This gives a source-backed explanation for possible warm-tab and input lag even when no requests run.
4. **Settings-based saves have multiple dependent requests.** A changed budget setting needs a read and a CAS write. A recurring bill edit can add a bill RPC, schedule update and conditional category or pairing updates. Ordinary ledger creates have one normal write RPC and apply its result to client state.

**Launch decision.** The source and local load test support keeping the current architecture for a 10–100-user pilot, subject to history correctness, native responsiveness and staging validation. Public-launch performance remains unverified. Old histories can degrade a single household before overall user count strains the database. Concurrent traffic adds a separate cost in CPU and queueing.

Each active session performs six local navigations per minute, one write per minute and one complete sign-in or refresh every five minutes.
