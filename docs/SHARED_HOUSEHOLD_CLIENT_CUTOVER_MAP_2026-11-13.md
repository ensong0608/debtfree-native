# Shared household client cutover map (2026-11-13)

**Purpose:** Source inventory for the client implementation after the shared-household plan review gate passes. This file records existing boundaries; it does not change app behavior.

## Current boundaries and required cutover

| Area | Current source boundary | Required implementation |
| --- | --- | --- |
| App bootstrap | `App.tsx` calls `loadUserOnboardingData(session)` on initial authentication and auth changes, then the app loads finance records using `userId`. | Load current server-verified memberships, select the device’s active household context only if it is still active, then load household settings/debts/finance under that context. Permission or membership uncertainty locks the view; do not fall back to another household’s cache. |
| Household identity | `createDefaultOnboardingData` derives `householdId` from the user ID; `UserOnboardingData` contains a household ID but no membership role/version context. | Add a typed context with authenticated user ID, selected household ID, server-confirmed role and membership version. A cached household ID is a selector hint only; server membership refresh is required before switching or mutating. |
| Household settings/debts | `src/onboarding-storage.ts`: `localStateKey(userId)`, `loadUserOnboardingData` reads Auth metadata and filters `debts.user_id`; saves use `debtfree_save_settings` in Auth metadata. Keep per-user onboarding/security/referral/appearance fields separate. Scope debt load/update/delete/reset to household RPCs; pass context and actor attribution explicitly. Retain the local acceptance fixture path. |
| Finance reads and commands | `src/finance-storage.ts`: `safeKey(userId, domain)`, pending journal and locks are user-keyed; `readCompleteFinanceDomain` filters by `user_id`; transaction RPCs are actor-scoped. Recurring bills use direct insert/update/delete; reconciliation anchors use direct upsert. | Namespace confirmed caches, pending rows, commands, locks and recovery proofs by user + household. Query by `household_id`. Route every finance mutation through an RPC enforcing household membership, role and the canonical lock order; use the authenticated user only as actor. |
| Pending journal | `src/finance/pending-journal.ts`: envelope v1 and each command contain `userId` only; journal lock/storage key is user-only. | Add a household-bound envelope/command version and membership version. Keep unresolved/dispatched/uncertain evidence in its old namespace and block household activation/deletion until authoritative recovery. |

Introduce household backup v2; only current household owners restore it. Bind restore baseline and receipt to household ID, retain exact merge semantics, and acquire the household finance mutex before the existing same-operation restore lock. |

Add context switch, invite/join, role change, remove/leave/transfer and destructive confirmations with owner/member/viewer gating. | Account deletion | `src/account-deletion.ts` invokes `delete-account` with an empty body; `App.tsx` clears local data only after a success receipt. | Persist and retry the same operation UUID; send the explicit empty-household deletion choice; show pending/uncertain fence state honestly. Clear this account’s local secrets/caches only after a verified final receipt; server membership revocation and Auth deletion must follow the durable fence. |

## Safe local migration sequence

1. Server-verify membership and selected context before loading shared data. Keep the prior cache under its original user/household key.
2. For each old user-only cache, copy only to the provable original household (the existing household ID from authoritative legacy settings); read back and validate user ID, household ID, row IDs and content before writing a committed migration marker. Do not copy an invitee’s cache into a joined household.
3. Keep the legacy copy until migration is committed and every pending command is either receipt-confirmed or explicitly retained for review. Uncertain operations block switching/activation.
4. Change every server query, mutation, restore and reset path in the same cutover before enabling invitation acceptance. The UI role checks are convenience only; server RPC/RLS is authoritative.
