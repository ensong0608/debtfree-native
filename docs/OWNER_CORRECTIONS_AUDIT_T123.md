# T-123 independent owner corrections audit

Verdict: **Changes needed.** Source review found a definite Light-theme regression in prominent amounts, incomplete smaller-cents coverage, and unresolved layout risks. The navigation, income accordion, month selection, and always-visible activity behavior are supported by source. No fresh native runtime certification is claimed.

## Findings

1. **High — AmountText bypasses appearance and text-scaling settings.** `src/components/AmountText.tsx:2,17` imports React Native Text directly. The app wrapper at `src/components/NativeAppearance.tsx:116` maps colors and applies the user's scaling preference; `src/components/FinancialScreen.tsx:229,233` supplies near-white `#F1F5F2` for `ui.title` and `ui.value`. Thus Budget income (`src/screens/BudgetScreen.tsx:655`), Home account balance (`src/components/FinancialScreen.tsx:210`), Debt account rows (`src/screens/DebtScreen.tsx:341`), and Progress totals (`src/screens/ProgressScreen.tsx:146,259`) retain near-white on Light surfaces. Hero amounts explicitly use `palette.onHero` and are a different case. Raw Text also ignores the app's disabled-scaling preference. Use the appearance-aware Text or apply equivalent mapping and scaling deliberately.
2. **Medium — smaller cents are inconsistent on prominent amounts.** Progress balance (`src/screens/ProgressScreen.tsx:121`) and Upcoming total and payment hero (`src/components/UpcomingObligations.tsx:278,360`) still use ordinary Text. These are prominent currency figures, so the owner example is not applied throughout. The helper preserves the supplied string by slicing and supplies the full accessibility label (`AmountText.tsx:13-18`); current formatter uses a decimal point. Its locale heuristic can mistake a lone grouping separator for a decimal in other formats, so it is not a general locale-safe parser. Nested font sizes have no explicit baseline adjustment; native baseline and screen-reader behavior require device verification.
3. **Medium — alignment and long-content resilience remain unproven and have concrete weak points.** The shared page uses 16px gutters (`FinancialScreen.tsx:219`), but Home's quiet sections add 18px internal padding (`HomeScreen.tsx:1299`) and account cards have their own inset; these must be evaluated as text columns, not equal outer padding. Debt reserves 26px for group totals (`DebtScreen.tsx:329`) and shrinks the right amount itself (`:340`), risking wrapped amounts with large values. Progress starting/current places two full amounts alongside a label without a shrink or wrapping policy (`ProgressScreen.tsx:231-236`); Budget income rows similarly have an unconstrained amount beside a flexible name (`BudgetScreen.tsx:725-737`). Home strategy and Transactions rows have flexible labels but unbounded amount columns (`HomeScreen.tsx:1148-1163`, `TransactionsScreen.tsx:925-952`); Upcoming has a flexible name (`UpcomingObligations.tsx:331-334`). These are source-based overflow risks, not observed runtime failures. Settings uses distinct 18px and 16px insets (`SettingsScreen.tsx:1257,1301`); sheet/form alignment and currency baselines need native visual verification at narrow widths and larger text before app-wide alignment can be certified.

## Manager corrections after audit

The source findings above describe the pre-correction snapshot. AmountText now imports appearance-aware Text, preserving palette mapping and text-scaling preferences for parent and nested decimals. It also keeps amounts on one line with bounded font fitting. Progress current balance and Utilization secondary totals, Upcoming total/payment hero, and Home Strategy amounts now use the helper. Income and category totals, Upcoming rows, Home trailing columns and Transactions amount columns have explicit width/shrink constraints. Starting/current activity balances are separate labeled rows to avoid squeezing two full amounts beside a label. No financial calculation, storage or payment changes were made. Native rendering, baseline alignment, narrow-device and larger-text behavior remain unverified.
