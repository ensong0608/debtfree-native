## Verdict and findings

**Not a clean acceptance.** Local hardening is present, but literal RPC isolation and reset-drop acceptance criteria are not met. Account deletion also has material recovery and future shared-household risks. Do not infer live readiness from local catalog evidence.

1. **Cross-owner existence disclosure and locking.** `20261106225931_phase1_financial_integrity_mutations.sql:174,356,614,738` selects transaction/anchor records by ID before checking owner; update/delete lock the other user's row before rejecting it. Different not-found and access-denied errors expose whether a supplied ID belongs to someone else; row locks can cause contention. Restore (`20261108173649...sql:307-313,353,407,466`) intentionally checks global tombstones and other-owner IDs and reports collision. Thus all reads are not strictly user-scoped, although inspected mutations use owner conditions and ownership is checked before returning row contents. Review the intended collision semantics and minimize existence disclosure/locking. This is not a finding of demonstrated cross-user financial mutation.
2. **Old reset not dropped.** `20261110210000...sql:10-11` explicitly revokes client execution rather than dropping it. Local catalog still contains `debtfree_reset_debts_atomic()` as SECURITY DEFINER, executable by postgres/service_role, alongside the new authenticated reset. This satisfies client retirement, not the requested drop.
3. **Deletion recovery is time-limited.** The Edge Function deletes Auth and then separately deletes tombstones; failure between these operations leaves tombstones. Retry depends on a still-valid JWT and gateway verification; once expired or session unavailable, the client cannot complete the retry and local data remains. A durable privileged cleanup/recovery mechanism needs design before release. Tokens may remain valid after user deletion; the retry branch relies critically on gateway JWT verification (`supabase/config.toml`, `verify_jwt = true`) and should never be exposed through an unverified invocation path. Deployment and real gateway behavior were not tested.
4. **Shared household deletion.** `households.created_by` cascades on Auth deletion and `household_members.household_id` cascades from household: deleting the creator removes the household and *all* memberships, including other users'. Financial tables have user-owned Auth FKs; no household FK was present in the local catalog for those records, so other members' financial rows can retain a now-orphaned household identifier. Define transfer/deletion semantics before enabling collaboration.
5. **Baseline is not proof of live equivalence.** `CREATE TABLE IF NOT EXISTS` does not reconcile existing columns, constraints, defaults or policies; the baseline enables RLS and creates policies if named policies are absent. It uses `IF NOT EXISTS` catalog checks, not the requested `EXCEPTION WHEN duplicate_object` pattern, and concurrent creation can race. Marking it repaired would only record history and would not validate or install schema. Compare actual live schema under separately authorized review before any repair; neither live safety nor repair was established here.

## Account deletion and cascades

`supabase/functions/delete-account/index.ts` parses the subject of the gateway-verified token, verifies an existing user with `admin.auth.getUser(token)` matching that subject, and calls `admin.auth.admin.deleteUser(userId)`. For an already absent user it relies on the valid gateway token for idempotent cleanup. `src/account-deletion.ts` requires a matching local session and server receipt before reporting success; failed Auth lookup is tolerated for retry. The local catalog shows Auth ON DELETE CASCADE for debts, transactions, anchors, recurring bills, profiles, households created by user, memberships by user, and receipt owner. Debt-linked transactions/bills use SET NULL and anchors CASCADE; trigger order and cross-owner references deserve isolated runtime testing. RPC-only triggers in `20261106225938...sql:16-55` reject only when `current_user` is anon/authenticated; privileged Auth cascade execution is not rejected on that condition. This is conditional on the actual privileged cascade execution context; this audit did not execute deletion.

Debt deletion creates tombstones via `debtfree_debt_tombstone_guard` (`20261106054656...sql:50-62`); tombstones have no Auth FK. The function deletes them afterward by `deleted_user_id`, returning 503 on failure. Auth deletion and cleanup are separate operations, so no atomic all-or-nothing guarantee exists. If deletion succeeds but response or cleanup fails, retry can succeed only while gateway accepts the original JWT; 404/readback and transient failures are handled as shown in source, but gateway, service-role privileges, timing and deleted-user JWT behavior remain unverified in this audit. Existing tokens are not inherently invalidated just because an Auth user was deleted; sensitive endpoints should account for that.

Following the independent `T-143` review, the Manager applied the following targeted remediations in [`supabase/migrations/20261111194422_security_and_performance_hardening.sql`](../supabase/migrations/20261111194422_security_and_performance_hardening.sql) and [`tests/financial-reset-contract.test.mjs`](../tests/financial-reset-contract.test.mjs):

## Manager Re-evaluation of Argon's Findings (2026-11-11)

This re-evaluation compares Argon's original findings with the local forward migration and current source. It does not connect to Supabase Cloud, deploy migrations/functions, or rerun tests. A read-only query against `supabase_db_supabase-audit-20261110` confirmed that the obsolete debt-only reset RPC is absent, the financial reset RPC is present, and the tombstone foreign key uses `ON DELETE CASCADE`.

**Assessment at the initial re-evaluation:** Argon's report correctly identified real pre-fix issues. The local migration then resolved two and reduced one, but the original strict-isolation acceptance criterion was still not met. Local verification was not evidence that Cloud had received those changes or that production was ready.

1. **Cross-owner probing and locks — partly resolved, residual remains.** The four transaction/reconciliation RPCs named in the hardening migration now scope the relevant transaction and anchor lookups and row locks by `user_id = v_uid`. This closes the original CRUD existence/locking issue in those functions. `debtfree_apply_snapshot_restore` still checks globally for tombstones and IDs owned by another user, then returns ID-specific collision errors (`20261108173649...sql:307-313,353-354,407-408,466-468`). That remains an existence oracle for a supplied ID, although there is no demonstrated cross-user data read or mutation and UUID guessing makes practical exploitation less likely. The restore RPC also takes `EXCLUSIVE MODE NOWAIT` locks on shared tables: it can fail fast if another write is active and can hold up writes by all users while restore runs. Treat this as an app-wide availability/serialization trade-off, not proof of a cross-user authorization bypass. Therefore the T-143 claim that all 11 authenticated RPCs have strict per-user isolation is **not satisfied**; restore's intentional global identity rules need an explicit decision and, if retained, generic collision errors should be considered.

2. **Obsolete debt-only reset — resolved locally, Cloud unverified.** The current hardening migration drops `debtfree_reset_debts_atomic()`. The local scratch catalog confirms it is absent and `debtfree_reset_financial_data_atomic()` is present. The migration has not been deployed to the active Cloud project, so this finding is not resolved there based on this review.

3. **Deletion cleanup — orphan window resolved locally, retry behavior unverified.** The new Auth foreign key cascades tombstones in the same database transaction as user deletion, and the trigger avoids creating new tombstones during that cascade. The local catalog confirms the cascade constraint. This removes Argon's specific risk that a failed second cleanup step leaves tombstones behind, provided the migration is deployed. The Edge Function's explicit tombstone delete is now redundant defense-in-depth, and its comment still incorrectly says tombstones have no Auth FK. The endpoint still depends on `verify_jwt = true` and gateway handling of a retry after Auth deletion; that behavior was not tested or deployed. A failed redundant cleanup can also return an error after the database cascade has already removed the rows, leaving the client without a success receipt even though backend cleanup completed.

4. **Household deletion — valid future lifecycle concern, not a current V1 blocker.** Deleting a household creator cascades its membership rows. If multi-member households contain other users' records, those records can retain an orphaned household ID. The repo's current access rules do not enable members to join arbitrarily, and the owner has deferred collaboration. Define owner transfer/deletion behavior before enabling shared households; do not treat this future case as a demonstrated current data-loss defect.

5. **Baseline and live equivalence — valid verification gap, not proof of a bad migration.** `CREATE TABLE IF NOT EXISTS` and name-only policy checks do not reconcile or validate a pre-existing live schema. The baseline and local replay establish a scratch bootstrap only; they do not prove the active project's schema or migration ledger matches the repo. The report's suggestion to require an `EXCEPTION WHEN duplicate_object` pattern is a style preference unless a concrete concurrent-creation requirement exists, and the race concern is not established as a production defect. Cloud comparison remains outside this review's authorized scope.

**Readiness conclusion at the initial re-evaluation:** The scratch database contained the local fixes, but T-143's strict RPC-isolation acceptance item remained open and the active project's migration state was not verified. No live data was accessed or changed.

## Follow-up Implementation: Restore ID Privacy (2026-11-11)

Added [`20261111194434_private_restore_identity_rekey.sql`](../supabase/migrations/20261111194434_private_restore_identity_rekey.sql) as a forward-only migration. It updates `debtfree_apply_snapshot_restore` to:

- Preserve IDs only when the matching row is already owned by the authenticated caller.
- Reject a debt ID in that caller's own tombstones, without echoing the ID.
- Assign fresh server UUIDs to all other incoming debt, bill, transaction and anchor IDs. This makes a foreign row ID, another user's tombstone ID, and an unused ID follow the same path; no cross-owner existence lookup is needed.
- Rewrite bill-to-debt, transaction-to-debt and anchor-to-debt/transaction references before merge conflict checks or writes.
- Keep other users' rows protected by the existing owner predicates and conflict clauses. The existing restore-wide `EXCLUSIVE MODE NOWAIT` locks remain; they can still affect writes by other users while a restore is in progress.

The restore protocol was updated to describe this behavior. The migration was applied to the local scratch project through the Supabase CLI and recorded as migration `20261111120000`. A transactional synthetic two-user check passed: caller-owned tombstones rejected without echoing the ID; active foreign IDs, a foreign tombstone ID, and an unused ID were remapped; bill, transaction and anchor references followed the remapped IDs; owner B's rows remained unchanged; and a subsequent restore preserved owner A's IDs. The test transaction rolled back, leaving no synthetic users or rows. This verifies local behavior only; no Cloud connection or deployment occurred. The restore-wide `EXCLUSIVE MODE NOWAIT` locks remain an app-wide write-contention trade-off. T-145 also corrected the stale account-deletion comments without changing runtime behavior.
