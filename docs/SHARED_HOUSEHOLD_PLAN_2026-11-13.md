## Current state and constraints

- `UserOnboardingData.householdId` is generated from the signed-in user ID (`src/onboarding-domain.ts`). It is an identifier, not proof of shared access.
- Household name, currency, and other onboarding settings are stored in `auth.users.raw_user_meta_data` under `debtfree_native_v1`. `debtfree_save_settings` binds `userId` to the caller and prevents changing `householdId`; those settings cannot safely represent one shared household yet.
- Debt, transactions, recurring bills, and reconciliation anchors are currently read/written primarily with `user_id = auth.uid()`. Current strict RLS intentionally grants no shared financial access. Early household policies are superseded by migrations `20261106054648_secure_household_debts.sql` and `20261106054719_strict_financial_rls_and_atomic_transactions.sql`.
- `public.households` and `public.household_members` exist, but client membership writes are closed. `SettingsScreen` currently shows only a local owner placeholder and says collaboration is unsupported.
- Secure local onboarding, finance caches, backup checkpoints, pending writes, revisions, account deletion, archive transitions, restore, and atomic financial RPCs are all keyed to the current user or current owner. Shared access must cover these paths, not only screen queries.
- Owner decisions require a three-person maximum, a dedicated Household editor, current settings/data safeguards, preserve onboarding for new/reset households, and never mutate prototype/production financial data. All existing financial rules, record IDs, archive semantics, deletion confirmations, and transaction identity rules remain in force.

## Proposed v1 product contract (review before coding)

1. **Membership cap:** Maximum three active members total, including the owner. A user may belong to multiple households and explicitly switch the active context. Accepting an invitation adds a separate membership/context; it never merges, moves, overwrites, or shares the invitee's existing household records.
2. **Roles:** `Owner` manages name/currency, invitations, roles, and membership. `Member` can read and perform normal finance edits, subject to current item-specific confirmation safeguards. `Viewer` can read but cannot mutate financial or household data. Only the owner can transfer ownership or delete the household. Enforce role rules server-side.
3. **Invitation:** Owner invites a normalized email address; invited person must authenticate as that exact address, and the server verifies it is the account’s current confirmed Auth email at acceptance. Lock or otherwise serialize the Auth identity read with email changes so stale/unverified addresses cannot accept. Reject changed or unconfirmed emails without consuming the invitation. Use an unguessable, single-use, seven-day token stored only as a hash. At most one live invitation per address; reserve an open slot at invitation time so active members plus pending invitations never exceed three. Acceptance rechecks the cap and all invite state atomically. Limit invite sends to five per household per hour. Creation, acceptance, expiry, revoke, and cap checks are server-atomic. Do not expose arbitrary client inserts/updates to membership tables. Invite and accept endpoints must not reveal whether unrelated emails have accounts.
4. **Shared data:** Household-wide settings and all supported financial domains resolve from the active household: debts and archive state, transactions, recurring bills, reconciliation anchors, income/household settings, payment matching, payoff settings, and category/link/split-plan preferences. Keep user-specific preferences (theme, text size, security) per-user. Keep immutable actor/audit identity for writes, while household ID is the authorization and query scope.
5. **Existing data on first sharing:** Preserve the owner's existing records and stable IDs. Attach only that owner's current household's records and settings in one reviewed, transactional migration/activation path. Do not infer or copy data from screenshots, another account, or a second member's private records. The invitee’s existing households and local financial data remain intact and private to those household contexts. Acceptance only adds the new membership; it never copies existing rows or settings into the invited household. If legacy local data cannot be reliably assigned to its prior household, quarantine it in the legacy namespace and do not expose it under the newly joined context. No data-empty check across devices is required because data is not merged.
6. **Revocation and account lifecycle:** Revocation takes effect on the server immediately; a removed member cannot read, write, retry pending operations, restore, or use another endpoint through stale membership. Household state remains for remaining members. Deleting a user account removes its memberships and personal settings but must not cascade-delete shared household data. Household ownership and data authority are separate from the creator's auth account; actor references are nullable/anonymized on account deletion while the household owner can continue managing retained records. Empty-household deletion/ownership transfer must be explicit and atomic.
7. **Offline and recovery:** Key local financial snapshots, pending journals, backup checkpoints, and recovery proofs by both authenticated user and household. Never replay an operation after the active household or membership changed. On access uncertainty/revocation, lock shared data and show a clear error; do not replace it with empty data or silently fall back to stale local state. Preserve pending-operation evidence for owner/review recovery without exposing it to a revoked member.
8. **No financial rule changes:** Sharing is an authorization, persistence, and collaboration change. No change to balances, payoff math, ledger inclusion, archive triggers, schedule/installment behavior, confirmation wording, or backup identity/merge semantics except the household scoping required to keep records together.

### Phase 1 — Server data model and authorization

- Add forward-only migrations for a durable per-household settings document with revision/CAS and household membership/invitation lifecycle. Keep Auth metadata for authentication and user-specific settings only; do not use it as the shared settings source.
- Add/backfill household IDs for all existing owner records transactionally, preserving stable row IDs and actor identity. Make household ID the durable data authority. Remove auth-user delete cascades from shared rows; retain actor IDs only as non-authorizing audit references, nulling/anonymizing them when an account is deleted. Update identity constraints and indexes to permit records authored by different members while preserving unique row IDs within a household. Keep each existing user-only household and records as a separate membership when that user joins another household; do not reassign historical records to the invited household.
- Replace user-only RLS with policy predicates based on active membership and role, with cross-record checks ensuring every linked debt, transaction, bill, reconciliation anchor, archive, and settings object belongs to the same household.
- Harden every `SECURITY DEFINER` finance RPC and settings/backup/account lifecycle RPC to derive caller identity from `auth.uid()`, look up active household membership, enforce role, lock household state where needed, and reject mismatched household IDs. No client-supplied household ID or user-editable Auth metadata/JWT claim is authority; query current membership and role from the server-side membership records. SECURITY DEFINER routines are retained only where required, use a fixed empty search_path, validate auth.uid() and active role, and have explicit grants revoked from PUBLIC/anon.
- Add transactional, rate-limited server operations for create/revoke/accept invitation, capacity checks, member removal, ownership transfer, account-deletion fencing, and safe household leave/delete. Enforce the three-person active + pending cap under concurrency. Deliver invitation links through a server-only mail path (for example, a narrowly scoped Edge Function); no service-role credential may enter the native client. Update `supabase/functions/delete-account` to use a durable per-account deletion fence with a locally unique operation ID and persisted dispatch state that survives the external Auth Admin API call. In one database transaction, acquire the same per-account lifecycle guard used by household creation and membership changes; lock all affected household rows in sorted ID order and membership rows in a fixed order; verify the account owns no retained households; establish the durable fence; and mark all of that account’s memberships revoked so current RLS/RPC membership checks deny stale-token access before the Auth call. Every operation that can create a household or add/transfer ownership or membership to that user must acquire the same guard first and reject a fenced account. Replace the `created_by` auth-user cascade with a non-cascading FK as defense in depth. Before calling Auth Admin, persist the attempt as dispatched and associate it with the operation ID; allow at most one outstanding external delete attempt per account. On success or authoritative “user absent” readback, finalize without restoring memberships. On timeout, lost response, or process crash with the user still present, keep the fence and revoked memberships in place; an existence check alone does not prove that the dispatched request cannot complete later. Reconcile the same attempt by operation ID. Clear the fence/reactivate memberships only if the Auth request was never dispatched or an authoritative terminal response proves the attempt cannot later take effect, followed by version-checked rollback. If the Auth API cannot establish that terminal guarantee, retain the fence/revocations and require reconciliation/manual recovery; do not unblock or issue a duplicate delete. All lifecycle operations use the canonical lock order documented in the cutover contract below: sorted account lifecycle guards, sorted household rows, sorted membership rows, the household-scoped financial mutex, affected financial/settings rows, then operation/fence rows. Do not acquire an earlier lock class while holding a later class. Concurrent owner transfer and account deletion must have one ordered outcome, and a household must retain a valid owner unless explicitly deleted empty.
- Preserve current exact item deletion/account-history safeguards, event-only archive rules, restore receipts, locks, and sync/recovery semantics when changing scope. Every finance mutation, account lifecycle command, and restore must participate in one household-wide revision/serialization barrier (or an equivalent proven CAS protocol) so a restore cannot race another member’s edit. Lock and revision checks cover every affected domain and are enforced in the database transaction, not by the UI.


#### Cutover concurrency and empty-household contract

- A client-supplied household ID selects the requested context only; every operation verifies the caller’s current active membership and role from database rows. A member can belong to multiple households. Never infer the active household from creator attribution or a JWT claim.
- Canonical lock order for authenticated writes and lifecycle changes: (1) acquire lifecycle guard locks for every participating Auth user UUID in sorted UUID order; (2) lock affected household rows in sorted household-ID order (`FOR SHARE` for ordinary member writes, `FOR UPDATE` for lifecycle transitions); (3) lock affected membership rows in `(household_id, user_id)` order and verify active status/role; (4) acquire the household-scoped financial advisory mutex; (5) lock affected settings and finance rows/tables in a deterministic table order then stable row identity; (6) lock/write invitation, restore-receipt, deletion-operation, and fence rows. Read-only checks may occur before locks only when they do not influence authorization or mutation. The current user-scoped finance mutex must be replaced with the household key so every member of one household serializes on the same key. Revoke direct client DML on shared finance tables and route every mutation through an RPC. No path may acquire an earlier lock class while holding a later one.
- Restore follows the same sequence: authenticate and verify active owner membership; acquire the selected household and membership locks; acquire the household finance mutex; lock the affected settings/debt/bill/transaction/anchor/tombstone data in the agreed deterministic order; only then acquire a same-operation lock keyed by `(household_id, operation_id)` and read/write its receipt. The existing user-only finance lock and operation lock/receipt check before household verification must be moved after household authorization and the household mutex; receipt identity binds household ID and payload. Use current v1 receipts/checkpoints only for their original owner and household identity. A v1 recovery may return a validated existing receipt but must not replay into a different household; new shared backups/receipts use v2 household identity and remain owner-only for restore.
- Multi-actor operations identify all known participants and households before locking: ownership transfer locks old and target owners; invite acceptance locks inviter/household owner and invitee; removal/role change locks acting owner and target; account deletion locks the deleting account and discovers its current households before household locks. After guards, household rows, and sorted membership rows are locked, re-read the complete affected membership/household set and compare it with the discovery snapshot. If the set changed or a newly required earlier lock was not acquired, abort the transaction with a retryable serialization outcome; retry the same operation ID from the beginning. Never acquire an earlier lock class after a later one.
- Shared finance records have a populated household ID as their authority after cutover. While nullable IDs remain during staging, every existing null-ID row must either be deterministically backfilled under a locked migration preflight from a unique, proven pre-sharing owner mapping, or the cutover must abort and keep sharing disabled until the row is quarantined/reconciled. Never assign an ambiguous row by choosing the first/current membership. This rule also applies to `debtfree_deleted_debt_ids` and `debtfree_deleted_bill_ids`: add household IDs and backfill each existing tombstone using the same unique, proven legacy owner mapping; if any tombstone cannot be attributed, abort the whole cutover or preserve it in quarantine and block all affected household activation and destructive operations until owner review. Never drop/recreate a tombstone without preserving its exact deleted identity. Every read, mutation, restore, reset, tombstone, and deletion path rejects or excludes null-household rows; if an unassigned row or tombstone could belong to the selected household, that household’s context and destructive operations fail closed. After cutover, household IDs are mandatory. A write omitting household ID may be server-derived only while the actor has exactly one active household membership; omission with multiple memberships is rejected and the updated client must pass its selected context. A supplied ID must match active membership and every linked debt/bill/anchor/tombstone must match that household. `user_id` is only nullable actor attribution, set to `auth.uid()` on new writes, and never authorizes access.
- Account deletion may delete an owner household only when the caller is the **only active member** and is the active owner, no active or pending invitation reserves a slot, and the household is empty. Recheck the sole-member condition while holding household and membership locks. Emptiness is checked while holding the household row and household financial mutex after in-flight writes finish. Require no debt (including archived), transaction (including soft-deleted), recurring bill, reconciliation anchor, debt/bill tombstone, or legacy null-household row with uncertain attribution; and no user-entered financial settings. Settings count as empty only when income is zero/absent, additional incomes and all schedules, debt/bill split plans, `mortgageEscrowByDebtId`, `mortgageExtraPaymentByDebtId`, `loanBillPairingByDebtId`, `recurringBillCategoryLabelByBillId`, and archive maps are empty, extra payment is zero/absent, strategy is default Snowball, and no unknown non-identity settings exist. Household name, currency, country, and time zone alone do not count as financial data. Malformed or uncertain state means non-empty. Mark an explicitly selected empty household pending deletion and remove only after Auth deletion is confirmed; a terminal rollback reactivates it only by version check.
- While a household is pending deletion, deny finance reads and all finance, restore/reset, settings, membership, invite, and ownership mutations. Only the service-side deletion finalizer for the same operation or a version-checked terminal rollback may change its state. This also prevents a member or invite operation from repopulating the household after the empty check.
- Pending client commands are part of the deletion preflight. Any unresolved, dispatched, or uncertain operation blocks context activation and account/household deletion until authoritative readback or explicit recovery resolves it.
### Phase 2 — Storage and cache context

- Introduce a typed household context and pass it through loaders, mutations, finance commands, settings saves, and RPC adapters. Switch queries from owner-only filters to household filters after server membership has been verified.
- Change household-wide settings CAS/revision to a household key; keep per-user settings separate. A conflict must return the authoritative household revision and never fall back to stale settings.
- Namespace local caches, pending journal entries, checkpoints, and migration markers by user + household. Bind each pending command to household ID and membership/session version; cancel replay when the identity/context no longer matches. Before enabling sharing, preflight every pending command: resolve confirmed operations from authoritative receipts/readback before retry; if an operation remains uncertain or unresolvable, stop household activation and preserve its evidence for explicit review. Never discard unresolved commands or replay them against another household.
- Migrate existing local keys idempotently and crash-safely: write a validated copy to the new namespace, read it back and verify identity/content, commit a migration marker, and only then retire the legacy key where safe. Keep a recoverable original through interrupted migration and never copy an invitee’s personal cache into the joined household. Include lost-response and interrupted-migration paths.
- Make successful empty data distinct from permission denial, unsupported schema, offline/stale cache, partial reads, and server errors. Keep existing stale/unknown data safety and sync status honest.
- Version backup and restore contracts. Existing v1 owner-bound backups, checkpoints, and receipts retain their original user/household identity and are never reinterpreted as shared-household artifacts. Every restore and every write-producing recovery, including legacy v1 recovery, requires current active-owner authorization at the database boundary plus the original identity and exact receipt checks. If the prior actor is no longer the current owner, retain the checkpoint and stop for review; never replay it. New v2 household backups bind to household ID and export version; retain exact record IDs, linked identities, archive state, and conflict semantics. Only the active household owner may restore v2, after current membership, household-wide baseline, and authorization checks. A restore lock/revision barrier serializes against all member edits; ambiguous identity mappings or stale baselines fail atomically without changes. Interrupted v1/v2 restores resume through their exact receipt or stop for review, never start a duplicate restore.
