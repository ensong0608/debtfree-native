# T134 independent design review

**Verdict: revise the design study before owner approval.** This is a focused navigation and refresh mockup with synthetic values, not a full native implementation. The owner references show a floating capsule with a high-contrast expanded selection and a separately accessible Add action; the proposal follows that direction. No native implementation is authorized until explicit owner approval.

## Actionable findings

1. **Progress navigation is missing.** The proposal renders Activity and a locked milestone directly but omits the existing Overview / Utilization / Milestones inner sections and period selector. This conflicts with preserving current inner sections and makes it impossible to judge the dock alongside them. Represent those section controls and preserve the always-visible account activity and permanently expanded payoff milestones in their appropriate sections; a complete product implementation is not needed for this study.
2. **Offline preview can become a false success.** `refresh(true)` shows offline after a timer, but the next pull or Preview refresh unconditionally calls `refresh()` and reports ?Updated just now,? without a simulated reconnection. Maintain an explicit simulated offline condition until changed, or clearly label the controls as independent scenarios and avoid suggesting connectivity was restored. Show that failure retains the displayed data and pending state; no realtime claim.
3. **Demo modal keyboard focus is incomplete.** Opening focuses the input and Close returns focus, but `aria-modal` is asserted without focus containment, Escape handling, or background inertness. Keyboard users can reach obscured controls, and refreshing from the external controls while the sheet is open can misrepresent an actual in-app gesture. Add an accessible demo dismissal/focus model and a clear way to demonstrate draft retention, or explain the limitation explicitly in the study.
4. **Narrow caption and notes disagree.** At container widths of 380px or less, all in-button labels disappear and a single selected caption appears below the dock; notes claim five icon-and-label targets. The fallback preserves programmatic button labels and 44px minimum widths, but does not retain the reference's expanded labeled pill. Correct the notes and present the compromise for owner review; verify all five selected states, especially Transactions, at narrow widths and large text before implementation. Below the width needed for five 44px targets plus gaps and padding the layout cannot fit; define a supported minimum.

## Source review observations

- Tab order is Home, Debt, Transactions, Budget, Progress. Debt has Accounts / Strategy, Transactions has History / Upcoming / Scheduled. `[hidden]` overrides the action's display rule, so Home and Progress have no Add; the other three use the requested action names. The footer is positioned over the scroll area and the 165px bottom padding exceeds its nominal action-plus-dock height, leaving room for the tenth Debt row at standard text size. This is a geometry assessment, not a device or enlarged-text certification.
- Dock buttons declare at least 44px width and 52px height; icon boxes are 30px with CSS-drawn shapes. The active dark pill uses a light foreground surface, consistent with the reference. Theme tokens provide distinct foreground/background colors, but contrast and clipping across all five states and themes were not measured or visually verified here.
- Refresh updates only the status text; it does not restart the app, navigate, render new page data, send requests, or mutate the draft. Route and section remain in memory during the simulation. Pending-write preservation is a stated future contract, not something the demo proves. Pointer gestures and browser controls are not evidence of native gesture arbitration, safe-area fit, screen-reader behavior, or persistence.
- The owner images also show the former Add at the bottom of content, reinforcing the need for the new fixed action. The mockup uses representative simplified screens; omitted unrelated interactions do not by themselves require a full implementation.

**Review evidence:** current proposal HTML and T133 notes; AGENTS, current preferences, app plan, prototype references, T133/T134 tracker entries, existing Progress section declaration, and four supplied owner images. Manager-reported renders were considered but not independently rerun. No application code, backend, tests, builds, browser, or devices were used.
