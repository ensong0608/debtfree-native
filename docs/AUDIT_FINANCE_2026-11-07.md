# Financial, persistence and security audit — T-051

2026-11-07. Source inspection only; no execution, runtime acceptance, database access or deployment verification. Severity reflects potential impact, not a claim that a live system has these migrations installed. Examples are synthetic. The financial plan and decision register distinguish approved money, forecast and calendar policies from proposals and require coverage before historical claims (`NATIVE_FINANCIAL_PLAN.md:84`; `FINANCIAL_DECISION_REGISTER.md:5`, `:16`, `:25`). Historical implementation notes are not current runtime evidence.

## Findings

### F1 — High: Offline and uncertain writes lack demonstrated replay or complete resolution

`src/finance-storage.ts:276`–`:283` persists a transaction intent before attempting the RPC; offline or uncertain outcomes retain it (`:351`–`:376`). On reload, `loadFinanceRecords` reads pending maps (`:119`–`:122`), compares transaction rows to remote (`:219`–`:224`), and overlays bills and anchors (`:226`–`:227`); it does not submit unresolved intents. `src/finance/storage-domain.ts:100` resolves transactions only when remote matches. Pending bill and anchor maps are not equivalently reconciled in that load path. A bill save whose response was lost can remain pending even if the server has the row; a genuinely offline transaction remains local after reconnection. Reconciliation saves separate anchor and adjustment intents (`src/finance-storage.ts:810`–`:822`), but those rows alone do not preserve a replayable atomic command with expected revision. Settings sign-out warning checks transaction IDs (`src/screens/SettingsScreen.tsx:434`–`:443`), not all pending domains. Risk: persistent divergence and no safe recovery path. Inspect recovery UI and establish an explicit recovery policy before changing it.

### F2 — High: Past-due history is inferred from present terms

`src/finance/payment-matching.ts:353`–`:369` starts in the creation month. `:392`–`:399` checks only that creation is not in the future, then emits any earlier due day within that same month. For example, a bill created November 20 with due day 5 is shown overdue November 5 on November 21, before it existed. The same applies to debts (`:440`–`:448`). Each historical cycle uses the current bill amount (`:406`) or current debt minimum (`:443`, `:455`), despite no effective-dated historical terms or verified opening coverage in this selector. An old minimum change or pre-existing account with missing recorded payments can produce incorrect overdue sums. Home and Budget consume this selector (`src/screens/HomeScreen.tsx:178`, `src/screens/BudgetScreen.tsx:727`); consistency between them does not establish truth. Preserve unknown/partial history and decide first-cycle and terms-change policy.

### F3 — High: Snapshot changes can be presented as earned progress

`src/onboarding-domain.ts:378`–`:386` defaults missing original balance to the entered balance, and `:456`–`:459` derives a starting total from current/original snapshots. Progress labels its derived percentage “paid down” (`src/screens/ProgressScreen.tsx:80`–`:82`, `:103`–`:110`) without establishing cause or coverage. `src/finance/progress.ts:168`–`:192` counts zero-balance snapshots as paid-off accounts; its current-month path does not establish a payoff during that month, and previous-month reconstruction assumes all subsequent changes are recorded. The screen also calculates milestones from these inputs (`src/screens/ProgressScreen.tsx:72`–`:75`); the selector counts zero-balance accounts (`src/finance/progress.ts:331`–`:343`). A manual correction from 100 to 0 can look like payoff progress without a payment or payoff event. This conflicts with the plan's coverage and event distinction (`NATIVE_FINANCIAL_PLAN.md:84`, `:94`). Repository-wide symbol search finds no production consumer of accountsPaidOffCount: calculateActivitySummary returns it (src/finance/progress.ts:195?:205), but Progress uses other summary fields (src/screens/ProgressScreen.tsx:138?:201); other references are tests. Its period count defect is latent, not a currently displayed count. Separately, the snapshot paid-down label and zero-balance-derived milestone calculations are exposed on Progress (src/screens/ProgressScreen.tsx:72?:82, :103?:110), so their misleading presentation remains an active source-level risk.

### F4 — High: Legacy debt-only reset remains callable in migration source

`supabase/migrations/20261106130000_phase1_rpc_only_financial_writes.sql:155`–`:168` exposes an authenticated security-definer RPC that deletes the caller's debts only. The schema sets transaction and bill account references to null, and cascades anchors on debt deletion (`supabase/migrations/20261106054714_transactions_bills_reconciliation.sql:11`, `:78`, `:113`). A direct authenticated call can therefore leave detached transaction/bill history and delete anchors, despite the disabled Settings reset control (`src/screens/SettingsScreen.tsx:1200`). The client also retains a fallback to this RPC (`src/onboarding-storage.ts:456`–`:457`). The newer atomic reset migration is a local artifact, not evidence of deployment or revocation of the older function (`supabase/migrations/20261106140000_reset_financial_data_atomic.sql:10`, `:57`–`:58`). Review actual privileges and dependencies in an authorized isolated environment and retire or replace the unsafe entry point through a separately approved migration.

### F5 — Medium: Concurrent pending-map writes can overwrite each other

Each mutation reads a whole pending map, changes an entry, then rewrites it (`src/finance-storage.ts:276`–`:279`, `:403`–`:406`, `:622`–`:625`). Two overlapping operations can read the same map and the later write can discard the other's intent; success/error cleanup similarly rewrites captured maps (`:308`–`:309`, `:342`). Call-level controls reduce but do not eliminate overlap: Transactions uses separate savingTx, savingEdit and deletingTx controls (src/screens/TransactionsScreen.tsx:75, :95, :230, :305, :362?:367, :631, :1050, :1071), while central add/update/delete handlers call commands without a shared lock (src/OnboardingAndHome.tsx:411?:469). Budget also invokes transaction update and payment callbacks (src/screens/BudgetScreen.tsx:240?:241, :271?:290, :307?:308); Home passes callbacks through (src/screens/HomeScreen.tsx:709?:712, :730?:733). Home?s savingRef protects its own debt operations (src/screens/HomeScreen.tsx:364, :425?:427, :443?:452), not a shared transaction-domain lock. Separate mutation paths can overlap, though an actual interleaving or device failure has not been demonstrated. It matters most when connectivity is lost or responses are ambiguous. Serialize per-user domain mutations or use transactional per-operation storage, and verify interrupted/concurrent saves with synthetic records.

### F6 — Medium: Reconciliation summary net change can disagree with its balance

`src/finance/ledger.ts:185`–`:198` applies only principal for an allocated payment and applies zero for an Auto loan payment with unknown principal. Yet `calculateReconciledBalance` totals the full payment amount (`:281`–`:282`) and calculates `netChange` from full charges minus full payments (`:287`), while `currentBalance` uses the different delta (`:275`–`:276`, `:293`). For a 100 Auto balance and a 20 payment without principal allocation, current balance remains 100 but net change reports -20. Repository-wide symbol search finds the exported selector only at its definition and in tests (src/finance/ledger.ts:218; tests/finance-ledger.test.mjs:8; tests/finance-phase1.test.mjs:11), with no production consumer. No downstream UI fields are shown from this selector; this is a latent defect, not an established user-facing issue. Derive balance change from actual deltas and keep cash payments separately labeled.

## Observations and limits

- Source safeguards include currency validation and checked money primitives; month-end due-day clamping (`src/finance/recurring-bills.ts:41`–`:52`); a monthly payoff engine with distinct shortfall, non-amortizing and horizon outcomes (`src/finance/payoff.ts:28`–`:30`, `:90`–`:112`); and pending transactions excluded from recorded activity (`src/finance/progress.ts:113`–`:115`). These observations are not independent numerical or runtime acceptance.
- Auth isolation has explicit client user checks (`src/onboarding-storage.ts:107`–`:109`, `src/finance-storage.ts:168`–`:176`) and SQL user-scoped policies (`supabase/migrations/20261106054719_strict_financial_rls_and_atomic_transactions.sql:18`–`:28`, `:61`–`:71`). Atomic transaction functions use authenticated identity and debt revision checks (`supabase/migrations/20261106120000_phase1_financial_integrity_mutations.sql:71`–`:75`, `:217`–`:228`); direct ledger writes are revoked in later local migration source (`supabase/migrations/20261106130000_phase1_rpc_only_financial_writes.sql:8`–`:10`). These do not prove deployed migration order, grants, RLS, cross-user isolation, or actual CAS behavior. Bills retain direct writes and require separate concurrency review.
- Automatic recurring background posting, real biometric gating and full reset are recorded deferrals, not audit blockers. The disabled reset control does not remove F4's callable SQL surface.
- `moneyFromMajor` uses floating-point conversion and `Math.round` (`src/finance/money.ts:24`–`:27`); inspect callers and signed rounding boundaries before asserting a specific user-visible rounding failure. Calendar uses household-zone date derivation (`src/finance/calendar.ts:45`–`:50`, `:67`–`:71`), but native IANA support and boundary behavior remain runtime verification gates. No broad claim of payoff or money correctness follows from this review.
