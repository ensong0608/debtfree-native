### Prioritized source findings from the manager follow-up

1. **High — Signed-out prototype preview is reachable in the current source.** `RootApp` defines `continueAsTestUser`, immediately sets prototype onboarding data and the `home` stage, then seeds storage under the fixed `test-user-preview` ID (App.tsx:335-339). It passes `onTestUserSignIn={continueAsTestUser}` unconditionally to `DebtFreeFlow` (App.tsx:341-368); the welcome and sign-in views render a pressable whenever that callback exists (src/OnboardingAndHome.tsx:769-779, :906-918). The audited path contains no `__DEV__`, environment, or auth guard. As currently wired, a signed-out user can choose “Preview Prototype Household” and skip sign-in; this is a confirmed release-blocking source path, not a hypothetical bypass. Gate/remove it from release builds before delivery and verify reachability on the release candidate.
2. **High — Backup transfer is developer-only and not full persistent restore.** The Settings blueprint requires export full backup, restore recovery checkpoint and import full backup (references/PROTOTYPE_INTERACTION_PATTERNS.md:184-190). Native Settings renders its Developer Tools and transfer modal only inside `__DEV__` conditions (src/screens/SettingsScreen.tsx:1214-1217, :1347-1349). Export JSON contains `onboardingData`, `transactions`, `recurringBills` and `reconciliationAnchors` (same file:693-705), so its payload shape covers those four in-memory domains. The ordinary v1 import validates onboarding data and calls only `onUpdateOnboardingData` (same file:767-781); the supplied callback updates app state (App.tsx:352-355), while exported transactions, bills and anchors are ignored. It does not restore a recovery checkpoint. The prototype-format branch converts records and calls the state callbacks, but first invokes `seedPrototypeHouseholdToStorage(userId)` rather than persisting the imported converted records as a full native restore (SettingsScreen.tsx:750-763). Thus there is a developer snapshot export, but full persistent ledger/bills/anchors recovery is absent or partial and the required checkpoint flow is absent. This does not satisfy the blueprint's backup/recovery interaction. Define and verify an explicit full-domain recovery contract before claiming backup support.
3. **Medium — Light/System theme is partial.** Theme preference is stored and forwarded from HomeScreen to FiveTabShell (src/screens/HomeScreen.tsx:129-135, :659-671; src/screens/SettingsScreen.tsx:471-478). The shell resolves `isLight` using the preference and device scheme, then changes its root, tab bar, tab labels/icons and settings overlay (src/FiveTabShell.tsx:30-31, :58-89). Shared financial UI tokens remain fixed dark colors (src/components/FinancialScreen.tsx:193-227, :240-304), and screen-specific styles also contain hardcoded dark colors (for example src/screens/ProgressScreen.tsx:433, :456; src/screens/SettingsScreen.tsx:1440). Thus saved preference and partial shell response exist, but app-wide Light/System rendering is not implemented consistently. Record theme as partial until screen surfaces and controls use a shared theme and are checked in both modes.

These findings update delivery risk without changing the historical acceptance record. The product audit independently identifies current source mismatches in mandatory mechanics; historical device acceptance proves only that those flows worked at the recorded checkpoint, not that the present working-tree snapshot still satisfies them (docs/AUDIT_PRODUCT_2026-11-07.md, “Mandatory interactions”). In particular, the current product audit reports the Home category/mortgage mismatch, missing strategy-card body target, replacement debt view instead of the required modal, and missing prescribed Budget month picker/general spending editor interactions. Preserve the T-046/T-049 reports as historical evidence and use the current source findings for present acceptance; do not state that all mandatory interactions currently pass.

## Delivery gates still open

### 1. Product and platform scope

- **Sandbox/test identity:** Expo metadata names the app “DebtFree Native Test,” slug `debtfree-native-test`, version `0.1.0`, and package/bundle IDs `com.debtfree.nativetest`; the extra environment is `sandbox-only` (app.json:3-24). README says no app store deployment is configured and the existing web production project must not be used (README.md:7-9). A production product name, identifiers, environment separation, data migration/retention policy and launch configuration are not recorded here.
- **Android release signing:** The private test APK workflow runs only on branch `codex/dfn-002-native-auth` and only when the workflow or `app.json` changes; it uploads a seven-day private artifact (.github/workflows/android-test-build.yml:1-5, 28-36). The generated Android release variant signs with the debug keystore and says to generate a production key (android/app/build.gradle:111-130). This is a test artifact pipeline, not store-ready signing or a general release process.
- **iOS:** There is no checked-in `ios/` project or `eas.json` at this snapshot, and Apple sign-in is only attempted when the platform is iOS and an environment flag is true (App.tsx:117-130). README documents Apple sign-in as unverified and lists Apple developer capability, sandbox provider configuration, a Mac/Xcode build and device/simulator checks still needed (README.md:64-71). Tracker DFN-FINAL-REMEDIATION also explicitly defers iOS runtime and physical-device signing (TRACKER.md:62-67). No iOS build/signing/distribution acceptance is recorded.
- **Test route in source:** The signed-out prototype route has no release guard in this snapshot. `RootApp` passes `onTestUserSignIn` unconditionally (App.tsx:341-368), and `OnboardingAndHome` renders the preview button on both welcome and sign-in views when that callback exists (src/OnboardingAndHome.tsx:769-779, :906-918). Its handler enters Home without authentication and seeds the fixed `test-user-preview` ID (App.tsx:335-339). This is a confirmed release-blocking path; gate/remove it from release builds and verify the release candidate.
- **CI/release evidence:** The general CI workflow runs lint, typecheck and tests on pull requests and pushes outside `main` (.github/workflows/ci.yml:1-20). The Android APK job is narrowly bound to an old feature branch. There is no iOS build/signing/release lane or app-store deployment configuration found in the inspected root/config inventory. Existing scripts provide development launch, lint, typecheck and unit tests only (package.json:26-35).

### 2. Disabled integrations and settings that remain placeholders/deferred

- **Bank linking and subscriptions:** README explicitly says billing and Plaid/Finicity aggregation are disabled in the sandbox (README.md:9). Onboarding offers “Premium + Bank Sync,” but the choice only saves a plan preference and the screen says no charge or bank connection occurs in this test build (OnboardingAndHome.tsx:1684-1692, 1750-1797). No purchase or bank aggregation SDK appears in package.json dependencies (package.json:5-24). Decide the v1 offer and either deliver the real provider flows or remove the advertised capability before public availability.
- **Notifications:** Settings currently describes switches as saved preferences and says background scheduling is deferred (SettingsScreen.tsx:1128-1153); README likewise says local/push delivery is unavailable (README.md:9, 32, 39). A saved toggle is not a delivered reminder. Choose the launch notification scope and implement/verify permissions, scheduling, cancellation, timezone and delivery if reminders are part of the offer.
- **Biometric unlock, reset, collaboration, and theme:** Biometric unlock is explicitly unavailable and disabled in Settings (SettingsScreen.tsx:876-884). The reset control is disabled because the reset migration is unapplied and native biometric verification is absent (SettingsScreen.tsx:1191-1207). Multi-member household collaboration is expressly unsupported in this build (SettingsScreen.tsx:986). Theme is partial: preference storage and shell/tab styling respond to Light/System, while shared financial tokens and screen-level styles remain dark (FiveTabShell.tsx:30-31, :58-89; FinancialScreen.tsx:193-227, :240-304; ProgressScreen.tsx:433, :456). These capabilities must not be presented as fully supported until completed and checked across screens.
- **Help and legal:** The native Settings screen has Help & Guides, Privacy Policy and Terms of Service rows, but their “Open in Browser” destinations use `debtfree-dashboard.ensong0608.workers.dev` (SettingsScreen.tsx:75-105, 1160-1183, 1330-1337). The local modal presents short summaries, not full policy documents. No check of those external pages was performed. Provide and verify production-owned help/privacy/terms pages, ensure statements match actual native data flows and vendors, and configure a contact/support route before release. Their presence in the UI alone is not legal review or publication evidence.
